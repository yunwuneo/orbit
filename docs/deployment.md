# 部署与操作

## 日本 Linux 服务器

需要 Python 3.11+（含 `sqlite3`、`zoneinfo` 和系统时区资料）、系统 CA 证书、访问模型服务与 `api.notion.com` 的 HTTPS 网络。故事时区固定为 `Asia/Shanghai`；部署进程通过服务配置 `Environment=TZ=Asia/Shanghai` 显式统一为上海时区，服务器地理位置不影响故事日期。当前尚未提供目标服务器，因此以下是部署说明，不是部署记录。

1. 将代码放到 `/opt/orbit`，为服务建立专用 `orbit` 用户。
2. 创建其可写的 `/var/lib/orbit`，权限 `0700`。代码和配置仅需可读。
3. 将公开配置保存到 `/etc/orbit/orbit.toml`，将 `runtime.db_path` 设置为 `/var/lib/orbit/orbit.sqlite3`。
4. 将模型配置与 Notion Token 放入 `/etc/orbit/orbit.env`，权限 `0600`，由 root 管理。变量名见 `.env.example`，不要把真实文件提交到 Git。
5. 为 Notion 集成开放七个配置页面、日记子页面及记忆、生活事件、计划与约定数据源。运行会读取真实 schema；缺少属性或选项会阻塞写回，不会自行修改 schema。
6. 按实际 Python 路径调整 `deploy/orbit.service`，复制到 systemd 服务目录，执行 `systemctl daemon-reload`，再启动 `orbit` 服务。

不需要 pip 安装、Docker 镜像或 Node。根目录直接运行 `python3 -m orbit` 即可。服务的环境文件由 systemd 加载；终端管理命令可使用 `python3 -m orbit --config /etc/orbit/orbit.toml --env-file /etc/orbit/orbit.env check`，或将 `.env` 放在 TOML 同目录。优先级为进程环境变量 > 环境文件 > TOML。环境文件支持单行赋值、`export`、引号及注释，不执行 shell 或变量展开；不要把密钥放在命令行参数中。

部署前先在隔离的 Notion 副本和选定模型上完成联调。`check` 只证明独立 Token 可读取资料，不证明写权限或模型协议已通过。确认实际回应、时间、来源、计划状态和写后核对后，再指向正式数据。

## 正常运行

- `run` 持有进程级互斥锁，每轮再持有操作锁；第二个常驻进程无法同时启动。管理命令如遇正在进行的一轮会提示稍后重试，不中断正在提交的事务。
- 默认每 600 秒唤醒，使用前一游标到当前的实时窗口；超过窗口的部分登记为缺口。每次进程启动和 `resume` 都将游标定位到恢复时刻，不自动补剧情。
- `pause` / `resume` 持久保存状态，并把安全的运行状态放入待同步队列。暂停仍允许技术写回；不调用模型生成新生活。
- 模型和 Notion 请求有超时与有限重试。生成连续失败达到上限后，运行状态给出 `generation_blocked`；修复连接或资料后运行 `retry`。
- 所有正文生成、任务和消费游标在一个 SQLite 事务中提交；对外写入前持久保存发送意图。服务被强制停止后，会先核对待写任务。

## 写回与人工修改

事件、计划、记忆使用数据库实际属性名及类型。每个写任务有持久稳定标识，新增页面的来源字段及正文都携带标识；写后核对正文、属性和父数据源后才确认成功。

状态页保留人类原文，仅维护一个带来源和故事时间的 Orbit 生活快照块，完整历史随事件保存。运行页同样维护独立运行快照块，避免每十分钟向主页面无限追加技术流水。每日日记与既有记忆只追加增量，不替换原文或提升旧记忆的确认状态。

本工作区的真实联调发现日期属性会丢弃秒和小数秒。Orbit 因而将 Notion 日期属性明确作为分钟索引，事件及计划正文保留完整带时区时间；到期判断、完成校验与补写冲突检查使用正文中的完整时间。人工把日期改到其他分钟时，以人工日期为准，不继续沿用旧正文时间。日记按上海日期筛选，日期属性索引不会代替事件正文的实际时间。

生成结束后重新读取来源，若变更则丢弃未发布结果。计划更新只触及状态，以及原为空时的执行结果；写前核对页面指纹，保留原安排时间，另追加判断依据。受管理快照也只在内容与上次读到的一致时更新。

**Notion REST 没有用于这里的原子比较交换。** 写前核对和写后验证能发现常见并发修改，但不能保证消除最后一次读取与 PATCH 之间的竞争。正式联调前应核实多平台并发模式；对需绝对避免竞争的计划或快照，采用维护窗口或单写入者。没有把本地测试当作强一致性证明。

## 补写、冲突和日记

`status` 的 `gaps` 保存原始缺口；完成覆盖范围见 `backfills` 中任务的 `start/end/cursor/status`。原始缺口不删除，供审计。新补写任务必须完全位于一个缺口内，不能与本地已有生活区间或其他补写任务重叠。

`backfill` 默认最多执行 12 段，每段默认 600 秒。它持有操作锁，实时推进看到未完成补写任务也会等待。失败后用同一 ID 续跑；已经生成的一段先恢复写回，再从下一段继续。取消任务保留已经发生的历史和待写内容。

若 Notion 在补写窗口已有历史，则在模型调用前阻塞；模型识别后续事实冲突则写入运行页并将任务标为 `blocked`。不静默改写历史；管理员可在核实后取消任务。语义上的历史一致性仍需实际模型联调和人工验收。

补写不更新当前生活快照、不改变现在的计划状态。补写中形成的历史意图和对计划的判断与外部事件、主观反应、实际结果分开保存在事件正文。新长期记忆可按故事日期提炼或追加来源。

日记在常驻服务中整理前一天，手动命令也只接受已经结束的上海日期。它按事件时间与“已发生”状态查询，不包含待发生事件；没有事件就不生成空白日记。补写后执行对应日期的 `diary` 会追加新版本，记录实际生成时间、来源 ID 和原始缺口。

## 回执不明与恢复

`status.writes` 给出安全的错误类别、重试次数和任务 ID，不包含故事正文或凭据。错误概要同样排队同步到运行页。

1. 自动恢复先用稳定标识查找远端结果；完整一致就确认，不再发送。
2. 明确被服务器拒绝的请求可在退避后重试。
3. 超时、断线或服务端故障可能已经提交。找不到结果时继续有限核对，不重新创建，最终阻塞。
4. 管理员修复问题后先运行 `retry`、`sync`。只有确认远端没有结果，才对准确任务使用 `confirm-absent --verified-in-notion`；否则可能重复创建。

人类修改导致的 `Conflict` 不会自动被忽略。核对页面、恢复所需 schema 或调整人工冲突后再重试；不通过清空数据库绕过防重。若不能恢复原预期，可保持阻塞并人工处理，当前未提供任意丢弃已生成生活任务的命令。

## 存储与维护

数据库及锁放在单一持久目录，权限收紧；不要删除运行数据库来“重新启动”，否则会丢失缺口、消费和防重记录。需要迁移时，正常停止进程后移动完整数据库，使用原配置资源 ID。

成功读回后立即清除 outbox 正文。默认 30 天后删除已完成任务回执和来源指纹映射，保留很小的故事区间、待写任务、消费指纹及补写进度；SQLite 复用空闲页，不复制 Notion 大型原始响应。数据库覆盖记录会随时间缓慢增长，未来长期运行需要观察实际体积。

资料读取有可配置上限：全部有效/待确认记忆、未完成计划和人工待处理事件，加最近 12 条已发生事件与日志中最近 3 个子页面。达到单页、条目或总上下文上限会明确阻塞，不截断后冒充完整读取，不默用旧缓存。日期与来源保留；旧资料中的“今天”不自动转为现实今天。日记及大量未完成事项长期积累后需要整理或调整上限。

## 后续链升级与恢复

新增能力默认关闭，不改变现有三源配置的运行方式。先更新代码并停止旧进程；使用同一持久数据库启动管理命令时，会在事务内以 `PRAGMA user_version` 增量升级。旧 runs、consumed、outbox、缺口及补写记录保留；不要换空库绕过旧消费。

正式启用前，先在隔离区完成新增接口和模型语义验收。运行 `threads-schema --plan` 只读预检；管理员显式执行 `threads-schema --apply` 才建库和补属性。输出 `sources.threads` 后自行保存配置，再打开 `[continuation] enabled = true`。自动运行缺少源、属性、选项或正确关系目标时会报错，不降级写入无关联的生活事件。

建库前持久记录发送意图，丢回执后查配置中心下的稳定标识；查不到会保持不确定状态，禁止重新建库。不要删除初始化步骤记录来强行重试。属性 PATCH 中断后可再次预检/初始化，已完成的步骤会读回核对；现有属性、原数据源和人工正文不重建。事项视图需在 Notion 手工按“处理进度”分组，显示“下次检查、同步状态、原始事件、相关计划”；本实现没有用 API 创建视图。

首次启用登记已有输入基线，不自动重新回应历史邀请。`thread-adopt EVENT_PAGE_ID` 可显式接纳未决输入；有旧消费或原主观判断而无法恢复时保持冲突，不复制决定。`threads` 和 `thread THREAD_ID` 只显示本地状态、来源索引、任务及回执摘要。`thread-recheck THREAD_ID` 为同修订幂等排队；不会强制接受、制造回复或标记完成。

写回按持久依赖与资源顺序选择：上游核对后才执行下游，同一事项/状态页/计划页保持顺序。一个事项失败不阻塞无关事项；仍依赖共享状态的生成须等待。`retry` 同时重开被阻塞的角色任务和技术写入，保留不确定发送标志。人工修改受管理字段/块造成的冲突需要先核对，不通过重试覆盖人工内容。

重启/恢复把同一事项的过期检查合并为一次当前复评，保留原计划时间和错过检查计数；没有重放每个漏掉的窗口。日常推进、输入轮询、事项到期与写回重试独立计时，等待用单调时钟。补写不修改当前事项、调度、计划状态；历史输入过滤掉当前补充，不自动合并历史与活动事项。

后续链保留仍用于因果、防重和恢复的节点、边及写回回执。已核对正文仍立即从 outbox 清除；不保存完整原始模型提示词、响应或 Notion 历史副本。运行库会累积小型索引，长期规模尚未实测。新增能力已有本地与一次虚构隔离区真实验收证据；正式服务运行和服务器部署仍未验收，详见 [后续链实现记录](event-continuation-implementation.md) 与 [真实验收报告](event-continuation-live-acceptance-2026-10-16.md)。
